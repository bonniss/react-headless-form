---
title: Internationalization (i18n)
description: Translate labels, descriptions, validation messages and selected props with any i18n library; literal text, translatable props, and type-checked i18n keys.
---

BlueForm handles i18n at the **form orchestration level**, not inside field components. Labels, descriptions, and validation messages are translated **before** they reach fields.
Field components always receive ready-to-render strings.

```ts
label;
description;
errorMessage;
```

Fields should never need to know about locales or translation libraries.

### Basic setup

i18n is configured once during `setupForm`. i18n is completely optional. If no `i18nConfig` is provided, all text values are treated as plain strings.

```ts
const [Form] = setupForm({
  i18nConfig: {
    t: (message, params) => translate(message, params),
  },
});
```

### Translating validation messages

```ts
const [Form] = setupForm({
  i18nConfig: {
    validationTranslation: {
      required: "validation.required", // "{field} is required"
      minLength: "validation.minLength", // "{field}: at least {minLength} characters"
    },
    t: (key, params) => translate(key, params), // your translator
  },
});
```

Validation rules remain standard RHF rules. How `validationTranslation` works:

- It covers `required`, `min`, `max`, `minLength`, `maxLength` and `pattern` (not `validate`, whose functions return their own message).
- `t` receives the key and `{ field, <rule>: value }`: `field` is the translated label, and e.g. `minLength: 3` for `minLength`.
- It **replaces** the field's own message for that rule (`rules: { required: "Name is needed" }` shows the `validation.required` message). Leave a rule out of `validationTranslation` to keep per-field messages for it.

### Example: using i18next

```ts
import i18next from "i18next";

const [Form] = setupForm({
  i18nConfig: {
    t: (key, params) => String(i18next.t(key, params)),
    validationTranslation: {
      required: "validation.required",
    },
  },
});
```

```ts
{
  username: {
    type: "text",
    label: "form.username.label",
    description: "form.username.description",
    rules: {
      required: true,
    },
  },
}
```

### Text forms

`label` and `description` accept a `TranslatableText`:

| Form | Example | Result |
|---|---|---|
| key | `"form.username"` | `t("form.username")` |
| key + params | `{ message: "form.max", params: { n: 5 }, fallback: "Max" }` | `t("form.max", { n: 5 })`, then `fallback`, then `message` |
| literal | `{ text: "Họ và tên" }` | shown as-is, `t` is **not** called (v0.14+) |

Use the literal form for text that is not a translation key — e.g. labels loaded from a database — so your i18n library doesn't warn about missing keys:

```ts
label: row.isKey ? row.label : { text: row.label },
```

### Switching language

Pass a new `t` when the language changes (for example `t` from `useTranslation()`). Labels, descriptions and the error messages already shown follow it: fields with a validation error are validated again (fields without an error are not), and errors set with `setError()` are kept. Keep `t` stable between renders of the same language (as i18n libraries do): a new function is read as a language change.

### Custom error messages

Every error message goes through `t` when it is displayed (`errorMessage` from `useField()` / `useArrayField()`), like labels. So custom messages can be keys:

```ts
code: { type: "text", rules: { validate: (v) => v === "ok" || "errors.code.invalid" } },
// a schema message, a rule message, or a server error
form.setError("email", { type: "server", message: "errors.email.taken" })
```

What an unknown key gives is up to your `t`. A good choice is to return the key itself, as i18next does by default: plain-text messages then show unchanged next to translated ones.

```ts
const t = (key: string, params?: Record<string, unknown>) =>
  (dictionary[lang][key] ?? key).replace(/\{(\w+)\}/g, (_, name) => String(params?.[name] ?? ""))
```

Messages read directly from `formState.errors` are the raw keys. For messages with parameters, use `validationTranslation` (`{field}` and the rule value are filled in), or build the message with your own `t` inside a config rebuilt when the language changes: the field is validated again with the new function.

### Translating props

_Added in v0.14._

By default only `label`, `description` and validation messages are translated; field `props` are passed through untouched. List the props that should also go through `t` — string values and `TranslatableText` objects are translated, anything else is left as-is:

```ts
const [Form] = setupForm({
  i18nConfig: {
    t: (key, params) => i18next.t(key, params),
    translateProps: ["placeholder", "title"],
  },
});

// config
email: {
  type: "text",
  props: { placeholder: "form.email.placeholder" }, // translated
},
```

Only top-level props are translated, not nested values such as select options: each UI library shapes options differently (`data`, `options`, `<option>` children), so translate their labels where you build them, with your `t`, and let the adapter pass them to the library's prop.

### Type-checked keys

_Added in v0.14._

Register your key union once with module augmentation, and `label` / `description` (including `{ message }`) only accept known keys — typos fail at compile time. `{ text }` still accepts any string.

```ts
// i18n.d.ts
import type { I18nKey as AppKey } from "./i18n/keys"; // e.g. derived from your JSON

declare module "react-headless-form" {
  interface Register {
    i18nKey: AppKey;
  }
}
```

```ts
username: { type: "text", label: "form.username" }, // ✅
email:    { type: "text", label: "form.emial" },    // ❌ compile-time error
note:     { type: "text", label: { text: "Raw" } }, // ✅ literal
```

### When i18n is disabled

With `enabled: false`, `t` is not called: keys are shown as-is, `{ message }` shows its `message`, and `{ text }` its text.
