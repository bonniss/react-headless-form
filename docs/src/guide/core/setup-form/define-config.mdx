`defineConfig` is the second item in the array returned by `setupForm`.

```ts
const [ // [!code focus]
  Form,
  defineConfig, // [!code focus]
  Section,
] = setupForm(); // [!code focus]
```

:::tip
`defineConfig` is used throughout this documentation, but since `setupForm()` returns an array, you can name it anything.
:::

## `defineConfig` for nested structures

For flat form structures, `<Form<TModel>>` is enough as types flow naturally from `Form<TModel>` into the configuration. With nested structures, however:

```ts
type LoginData = {
  account: {
    username: string;
    password: string;
  };
};
````

You have two options: use dot notation keys — `account.username` — or use `defineConfig` if you prefer your config to mirror the shape of your data model, which is typically the case when using the built-in `section` type.

```tsx
const [Form, defineConfig] = setupForm({
  fieldMapping: defineMapping({
    text: InputField,
  }),
  renderRoot: ({ children, onSubmit }) => (
    <form onSubmit={onSubmit}>{children}</form>
  ),
});

const ComplexObjectForm = () => (
  <Form<LoginData>
    config={{
      account: {
        type: "section", // built in type
        config: defineConfig<LoginData["account"]>({
          username: {
            type: "text",
          },
          password: {
            type: "text",
          },
        }),
      },
    }}
  />
);
```

## `defineConfig` for reusable configuration

Another common use case for `defineConfig` is to define configurations once and import them wherever needed, while still preserving the same field mapping and typing rules.

```tsx title="form.setup.ts"
import { setupForm, defineMapping } from "react-headless-form";
import InputField from "./InputField";

export const [Form, defineConfig] = setupForm({
  fieldMapping: defineMapping({
    text: InputField,
  }),
  renderRoot: ({ children, onSubmit }) => (
    <form onSubmit={onSubmit}>{children}</form>
  ),
});
```

```tsx title="login.form.ts"
import type { LoginData } from "./types";
import { defineConfig } from "./form.setup";

export const loginFormConfig = defineConfig<LoginData>({
  username: {
    type: "text",
    label: "Username",
  },
  password: {
    type: "text",
    props: {
      type: "password",
    },
  },
});
```

```tsx title="LoginPage.tsx"
import { Form } from "./form.setup";
import { loginFormConfig } from "./login.form";

<Form<LoginData>
  config={loginFormConfig}
  onSubmit={(data) => {
    console.log(data);
  }}
>
  <button type="submit">Login</button>
</Form>;
```

## `defineDynamicConfig` for configs built from data

_Added in v0.14._

A config is plain data except for functions (`visible`, `validate`, …), so it can be generated at runtime — for instance from field metadata stored in a database. Such configs can't satisfy the compile-time checks of `defineConfig` (the `type` is just a `string`, `props` are unknown). Use `defineDynamicConfig` instead: it accepts a loosely typed object and returns a config `<Form>` accepts.

```tsx
import { defineDynamicConfig } from "react-headless-form"

// rows: { key: string; kind: string; label: string; pattern?: string }[]
const config = defineDynamicConfig(
  Object.fromEntries(
    rows.map((row) => [
      row.key,
      {
        type: row.kind,                       // must exist in fieldMapping
        label: { text: row.label },           // literal, not an i18n key
        rules: row.pattern ? { pattern: { value: row.pattern, message: "Invalid" } } : {},
      },
    ]),
  ),
)

<Form config={config} />
```

`rules.pattern` accepts a string (`"^\\d+$"` or `"/^abc$/i"`), so validation can be stored as data too. Unknown `type`s are not caught at compile time; they throw at render time like any unmapped type.
