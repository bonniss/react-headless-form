# Integrations

BlueForm renders no UI of its own, so it works with **any React UI library**: a library is wired in by writing one small adapter per field type, each reading everything from `useField()`.

## Live demos

Each demo below renders **the same form config** with a different library. Only `fields.tsx` changes. They are built from [`docs/integrations`](https://github.com/bonniss/react-headless-form/tree/main/docs/integrations) together with these docs, and served from the docs site itself.

| Library | Demo |
|---|---|
| [Mantine](./mantine.mdx) | Mantine v8 |
| [shadcn/ui](./shadcn.mdx) | Tailwind v4, shadcn-style primitives |
| [Ant Design](./antd.mdx) | antd v6, `Form.Item` for layout only |
| [Material UI](./mui.mdx) | MUI v7 |

Static recipes (no live demo yet): [Chakra UI](./chakra-ui.mdx), [PrimeReact](./prime-react.mdx), [Arco Design](./arco-design.mdx), [Semi Design](./semi-design.mdx), [TDesign](./tdesign.mdx), [React Native Web](./react-native-web.mdx).

## Sample form

The shared config shows most of the API in one form:

- `rules` with translated messages (`required`, `pattern`)
- JSON conditions: `adminCode` is **visible** only for admins, `bio` is **disabled** for viewers
- computed fields: an editable `slug` from the name, a read-only `addressCount` aggregate
- a nested `section` and an `array` field
- i18n (English / 日本語): labels are translation keys resolved by `i18nConfig.t`

`shared/types.ts` is the contract every library's adapters implement: the same props for `text`, `longText`, `select` and `checkbox`, plus three layout shells (`Root`, `Section`, `AddressList`). That is why the config type-checks identically for all of them.

## What changes, what doesn't

|                           | Changes                                          | Stays the same                            |
| ------------------------- | ------------------------------------------------ | ----------------------------------------- |
| **Field components**      | UI library imports, prop names, event signatures | `useField` call, destructuring            |
| **Section / array shell** | Layout component (`Card`, `Fieldset`, …)         | `render` prop pattern, `useArrayField`    |
| **Form config**           | Nothing                                          | Everything (rules, conditions, computes)  |

## Event signatures

`onChange` from `useField()` accepts a value or a native event, but passing the value explicitly is clearer:

| Library | Text input | Select | Boolean |
|---|---|---|---|
| Mantine | event → `e.currentTarget.value` | value | event → `e.currentTarget.checked` |
| shadcn/ui (native) | event → `e.target.value` | event (native `<select>`); `onValueChange` with Radix | event; `onCheckedChange` with Radix |
| Ant Design | event → `e.target.value` | value | event → `e.target.checked` |
| Material UI | event → `e.target.value` | event (`TextField select`) | event → `e.target.checked` |
| animal-island-ui | event → `e.target.value` | key (options use `key`) | `Switch` → checked |

## Bring your own library

1. Call `useField()` in a field component and destructure what you need.
2. Map `value` to the library's value prop and call `onChange(value)` from its change handler.
3. Wire `label`, `errorMessage`, `required`, `disabled`, `readOnly` and `id` (for label association).

## Validation libraries

Any [Standard Schema](https://standardschema.dev) works directly with the `schema` prop, no resolver package needed: see [Zod](./zod.mdx), [Valibot](./valibot.mdx) and [ArkType](./arktype.mdx). Other libraries use a resolver through `formOptions.resolver`: see [Yup](./yup.mdx) and [Ajv](./ajv.mdx), and [Schema validation](../../../guide/core/schema-validation.mdx).

## Running the demos locally

`pnpm dev` serves the docs; run `pnpm dev:demos` alongside to serve the demos (Vite, port 5180). `pnpm build` builds both.
