BlueForm translates at the orchestration level: field components receive ready-to-render strings (`label`, `description`, `errorMessage`) and never deal with locales. One function, `i18nConfig.t(key, params)`, connects any i18n library. Put `i18nConfig` in `setupForm`, or on `<Form>` when `t` changes with the language. All options: [i18n guide](../../guide/core/i18n.mdx).

## Translating labels and descriptions

`t` receives the string from the field config and returns its translation. BlueForm does not dictate a key format.

## Translating validation messages

`validationTranslation` maps the built-in rules (`required`, `min`, `max`, `minLength`, `maxLength`, `pattern`) to keys. `t` receives the key with `field` (the translated label) and the rule's value (e.g. `minLength: 3`), so the rules stay plain: `required: true`, `minLength: 3`. It replaces a field's own message for that rule.

Other messages — from `validate`, a schema or `setError()` — go through `t` too, so they can be keys as well: see [Custom error messages](../../guide/core/i18n.mdx#custom-error-messages).

## With an i18n library

Pass the library's translate function as `t` on `<Form>`: it changes with the language, so labels and the error messages already shown follow it, and the values are kept. Each example is one field: submit it empty, then switch the language.
